# 팀 협업과 검증 증적 보관

팀 검토용 초안

## 준영님용 이슈 배정

1. 팀 레포의 **Issues → New issue**에서 [팀 작업 이슈 템플릿](../.github/ISSUE_TEMPLATE/team-task.md)을 고른다. 목표, 바꿀 범위, 완료 기준, 검증 방법을 적는다. 동시에 진행하는 이슈가 같은 노트북이나 설정을 바꾸면 담당자와 작업 범위·병합 순서를 먼저 맞춘다.
2. 이슈 오른쪽의 **Assignees**에서 담당자의 GitHub 아이디를 선택한다. 팀원이 비공개 레포 초대를 수락했는지 확인한다. 이슈 본문과 담당자가 보이면 이슈 링크를 공유한다.
3. 여러 이슈를 같은 팀원에게 배정했다면 메시지에 먼저 할 이슈 번호를 적는다. EC2에서 시험해야 하면 이슈에 확인할 셀 또는 동작과 실행 담당을 적는다.

**배정 메시지 예시**

> #12 EC2–Colab 연결 가이드 작업을 배정했어요. 처음 접속하는 팀원이 가이드대로 연결해 실행 서버 확인 셀을 통과하면 됩니다. 팀 레포에서 Codex에 “저장소 규칙 읽고 배정된 작업 진행해줘”라고 요청해 보세요. [이슈 링크]

## 이슈 찾기

작업을 시작할 때 다음 순서로 이슈를 확인한다.

1. 사용자가 지정한 이슈 번호나 링크를 우선 사용한다.
2. 현재 브랜치가 `docs/12-ec2-colab-setup`처럼 이슈 번호를 포함하면 같은 저장소에서 해당 열린 이슈의 본문과 범위를 확인한다.
3. 브랜치로 특정할 수 없으면 로그인한 본인의 GitHub 계정에 배정된 열린 이슈를 조회한다. GitHub CLI가 연결돼 있다면 레포에서 `gh issue list --assignee "@me" --state open`를 사용할 수 있다. 한 건이면 진행하고, 여러 건이면 번호와 제목을 보여주고 어느 이슈를 할지 확인한다. 배정된 이슈가 없거나 조회 권한이 없으면 이슈 번호 또는 링크와 본문을 요청한다.

## Spec과 구현

구현 전에 목표, 변경 범위, 관찰 가능한 완료 기준을 이슈에서 확인한다. 명확한 내용은 바로 진행하고, 작업 범위나 성공 판정을 바꾸는 결정이 비어 있으면 그 항목만 확인한다.

- **작은 변경** — 문구 수정, 기존 기준이 분명한 버그 수정, 기존 절차 보완은 이슈 본문과 기존 가이드·Spec으로 진행한다. 완료 기준과 확인 방법은 이슈에 남긴다.
- **별도 Spec이 필요한 변경** — 공용 인터페이스나 로봇 동작 기준을 새로 정하거나 바꾸고 여러 작업에 영향을 주는 경우에 쓴다. 예를 들어 SO-101을 MoveIt에 처음 연결할 때는 관절 이름과 단위, 목표 자세 입력과 결과, 실패 처리, 완료 기준을 적는다. 기존 Spec이 있으면 갱신하고, 새 설계 문서가 필요하면 `docs/specs/<이슈번호>-<주제>.md`에 작성해 이슈에서 링크한다.

해당 이슈의 작업 브랜치가 있으면 이어서 작업한다. 새 작업은 최신 `main`을 기준으로 이슈별 브랜치를 만들어 구현한다. PR 본문에서 이슈, 변경 내용, 검증 기록을 연결하고 팀 검토 후 `main`에 합친다.


브랜치는 소문자와 하이픈으로 쓴다. 접두사로 주된 변경을 표시하고, 이슈 번호가 있으면 이름에 넣는다.

| 접두사 | 용도 | 예시 |
| --- | --- | --- |
| `docs/` | 실행 안내와 팀 문서 | `docs/12-ec2-colab-setup` |
| `feat/` | 로봇 모델, 시뮬레이션 등 기능 추가 | `feat/13-so101-scene` |
| `fix/` | 동작 오류 수정 | `fix/14-franka-controller` |
| `chore/` | 도구와 개발 환경 정리 | `chore/15-pin-sim-dependencies` |

## 커밋 컨벤션

커밋 제목은 `유형(영역): 변경 요약`으로 쓴다. 괄호와 영역은 선택이며, 영역이 분명하지 않으면 `유형: 변경 요약`으로 쓴다. 한 커밋은 검토할 수 있는 변경 한 묶음을 담는다.

괄호에는 영향을 받는 영역을 소문자로 적는다. `ec2`, `colab`, `cumotion`, `so101`, `amr`, `workflow`를 예시로 쓰고, 필요한 영역이 있으면 추가한다. 변경 요약에는 바뀐 동작이나 산출물을 적는다.

| 유형 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능이나 실습 동작 추가 | `feat(so101): 탁상 집기 장면 추가` |
| `fix` | 기존 동작 수정 | `fix(cumotion): Franka 관절 상태 수신 수정` |
| `docs` | 가이드·팀 규칙·인계 문서 변경 | `docs(ec2): Colab 연결과 서버 확인 절차 정리` |
| `test` | 검사 코드나 테스트 추가·변경 | `test(colab): 노트북 문법 검사 추가` |
| `chore` | 개발 도구·환경 관리 | `chore: 시뮬레이션 의존성 버전 고정` |

제목만으로 변경 이유가 드러나지 않으면 빈 줄을 두고 본문에 왜 바꿨는지, 어떤 제약을 해결했는지 한두 줄로 적는다. 이슈 번호와 검증 결과는 관련 PR에 남긴다.

## PR 열기와 공유

1. 작업 브랜치를 푸시한 뒤 GitHub에서 PR을 연다. **base**는 `main`, **compare**는 작업 브랜치로 선택한다.
2. [PR 템플릿](../.github/pull_request_template.md)에 관련 이슈, 변경 내용, 검증 결과·증적, 미실행·남은 작업, 리뷰 요청을 적는다. 이슈 완료 기준을 모두 충족하고 이 PR로 이슈를 끝낼 때 `Closes #12`를 쓴다. 이어서 작업해야 하면 `Refs #12`로 연결한다.
3. 검토할 팀원이 있으면 PR 오른쪽의 **Reviewers**에서 지정한다. 팀 채팅에는 PR 링크와 확인이 필요한 항목을 함께 보낸다.

**PR 공유 메시지 예시**

> #12 EC2–Colab 연결 가이드 PR 올렸어요. 기존 EC2에서 실습하신 분은 가이드의 접속 순서와 빠진 설정이 있는지 봐주실 수 있을까요? 의견은 PR 댓글로 남겨주세요. [PR 링크]

## 결과는 작업 위치에 맞춰 보관한다

| 위치 | 보관할 내용 |
| --- | --- |
| GitHub Issue | 담당자, 완료 기준, 진행·보류 상태와 다음 작업 |
| PR | 바뀐 점, 리뷰 요청 범위, 검증 요약과 증적 링크. 문서 수정처럼 간단한 작업은 PR의 확인 결과만으로 충분하다. |
| `README.md` | 팀원이 처음 읽는 실행 진입점 |
| `docs/guides/` | 여러 사람이 반복해서 따라 할 상세 절차 |
| `docs/verification/<이슈번호>-<주제>.md` | 시뮬레이터나 실물 장비의 재현 절차와 관찰 결과. 재실행 기록은 같은 문서에 날짜와 버전을 붙여 추가한다. |
| `docs/evidence/<이슈번호>-<주제>/` | 기록에서 링크하는 짧은 정제 로그와 판정에 필요한 스크린샷 |
| 팀 공유 드라이브 | 녹화 영상, 전체 로그, 데이터셋 같은 큰 파일. 검증 기록에 팀원이 열 수 있는 링크를 적는다. |

예를 들어 이슈의 실행 절차를 `docs/guides/ec2-colab-setup.md`에 적고, 실제로 접속을 검증한 결과는 `docs/verification/12-ec2-colab-setup.md`에 기록한다. 작성자는 GitHub에서 찾을 수 있게 이슈와 PR을 연결한다.

## 완료 기준

- **실험 이슈** — 실행 전에 확인할 질문과 판정 방법을 적는다. 사용한 환경·버전·장면·설정, 실제 관찰과 근거, 다음 판단을 기록한다. 결과가 기대와 달라도 그 근거로 질문에 답할 수 있으면 실험을 완료할 수 있다. 실행하지 못했거나 관찰만으로 판정할 수 없으면 재개 조건을 남긴다.
- **구현 이슈** — 이슈에 적힌 동작을 지정된 환경에서 확인하고, 완료 기준별 결과를 기록한다. 필수 동작이 실패하거나 아직 확인되지 않았다면 남은 작업으로 인계한다.

예를 들어 “수정 플러그인으로 Franka를 움직일 수 있는지 확인”하는 실험에서는 경로가 생성됐지만 가상 팔이 움직이지 않았다는 결과도 근거가 있으면 기록을 닫을 수 있다. “Franka가 계획한 경로를 따라 움직이도록 수정”하는 구현은 그 동작을 확인해야 완료된다.

## 작업별 검사

완료 기준에 맞는 행을 골라 검사한다. 여러 종류의 변경이 있으면 해당 검사를 함께 수행한다.

| 변경 | 기본 검사 | 완료 기준에 필요한 실행 시험 |
| --- | --- | --- |
| README·가이드·Spec | 링크, 파일 경로, 안내 순서를 실제 파일과 대조한다. | 실행 절차 변경이 범위에 있으면 대상 환경에서 안내를 따라 핵심 단계까지 확인한다. |
| Colab 노트북 코드 | 노트북 JSON과 변경한 Python 셀의 문법을 확인한다. 공유 파일의 셀 출력과 접속 정보를 점검한다. | EC2에서 선행 셀과 변경한 셀을 순서대로 실행해 기대 결과를 확인한다. |
| ROS 2 패키지·제어 플러그인 | 변경한 패키지를 빌드하고 관련 기존 테스트가 있으면 실행한다. | 대상 환경에서 플러그인 로드와 이슈에 지정된 경로 생성·실행 결과를 확인한다. |
| SO-101·RC카 실물 제어 | 관련 설정과 로컬에서 확인 가능한 명령 생성·변환을 검사한다. | 이슈에 정한 입력으로 실물 동작을 확인하고 관찰을 남긴다. |

Lint는 레포에 관련 설정이 있을 때 적용한다. 공유 EC2 노트북은 대상 셀만 순서대로 실행한다. 설치·복구나 컨테이너 재시작이 필요한 경우에는 공용 세션에 미치는 영향을 먼저 조율한다.

## 인계

변경과 검증 결과를 PR에 적고 상세 기록이나 증적을 링크한다. PR이 아직 없으면 인계 요약을 준비한다. 완료 기준별 판정은 `통과`, `실패`, `미실행`, `해당 없음`을 사용한다. 실행할 수 없는 검증은 이유와 재개 조건을 남기고, 완료에 필요한 검증이 남으면 다음 작업으로 인계한다.

## 검증 기록 양식

```markdown
# 검증 대상

- 이슈 / PR — #번호 / 링크
- 실행자 / 날짜 / 리비전 — 이름, YYYY-MM-DD, 확인한 커밋 SHA
- 환경 — 문서 검사, 로컬, 팀 EC2 또는 실물 장비와 관련 버전
- 재현 — 실행한 명령 또는 노트북 셀·조작 순서, 사용한 장면이나 입력
- 기대 / 관찰 — 기대 동작과 실제 결과
- 판정 — 통과 / 실패 / 미실행 / 해당 없음
- 증적 — 정제 로그, 화면 캡처 또는 공유 드라이브 링크
- 남은 범위 / 다음 작업 — 미확인 이유와 다음에 확인할 한 가지
```

Franka 실습에서는 **EC2 연결, 관절 데이터 수신, 경로 생성, 가상 팔 동작**을 각각 판정한다. SO-101 실물 시험은 사용한 장비와 관찰 결과를 따로 적는다. EC2 권한이나 장비가 없어 실행하지 못했다면 `미실행`과 이유를 기록한다.

공유 EC2의 시뮬레이터 실행이 겹치면 팀 채팅에서 실행 시간을 정한다. 증적을 공유하기 전 로그·스크린샷·노트북 출력에서 접속 주소, 실제 키 경로, 토큰을 확인하고 제거한다. 문서의 접속값은 예시값을 쓴다.
